Authentication

Three credential types, each for a different caller:

CallerCredentialHow
Demo playerdemo_token Issued by POST /api/v1/demo/sessions; sent as query param ?demo_token=…, which the client forwards as an Authorization: Demo … header.
Operator backend (server-to-server)HMAC keypair Four headers on every call: X-API-Key (public key id), X-Timestamp (unix seconds), X-Nonce (unique per request), X-Signature (hex(HMAC-SHA256(secret, canonical)) where canonical = METHOD\nPATH\nTIMESTAMP\nNONCE\nSHA256(raw_body)). PATH only — the query string is never signed.
Player clientSession token Authorization: Bearer <session_id> on game routes, or the gst_… launch token where a route accepts it. Tokens are short-lived; the shared HMAC secret is never embedded in a launch URL or returned to a player.

Demo URL

Create a demo session, then open the game with the returned token:

POST /api/v1/demo/sessions
{"game_slug":"teen-patti-pro","currency":"USD","lang":"EN"}

# then open:
https://api.ura-dhura.com/teen-patti-pro?demo_token=<demo_token>
No anonymous demo mode. A bare ?operator=demo&user=… query string does not authenticate anyone on this deployment. Demo play requires a demo_token from POST /api/v1/demo/sessions, or run the game process with --demo. An offline fixed-seed replay is also available at /teen-patti-pro/demo.html (no wallet, no live state).

Production URL (per player)

Your backend mints one session per player via POST /api/v1/sessions (HMAC-signed). The response contains launch_url — that is the per-player play URL. Opening it returns HTTP 302 to the game page with the session attached:

launch_url: https://api.ura-dhura.com/api/v1/provider/launch/<token>
  → 302 → /teen-patti-pro/?session=<token>[&room=<table_id>]

One session per player. Never share a launch_url between players and never put the HMAC secret in a URL.

Response Envelope

Every JSON response — success and error — uses one envelope:

{
  "success": true,
  "code": "OK",
  "message": "OK",
  "data": { "...": "..." },
  "serverTime": "2026-01-04T12:00:00+00:00",
  "serverTimeMs": 1767528000000,
  "requestId": "9f2c…"
}

Errors keep the same shape with "success": false and a machine-readable code (e.g. BETTING_CLOSED, INSUFFICIENT_BALANCE, STATE_CONFLICT, WALLET_UNAVAILABLE, WALLET_NOT_CONFIGURED). HTTP status mirrors the outcome (401 auth, 404 unknown, 409 conflict, 422 validation, 429 rate-limit, 503 wallet).

Sample: Mint Session

TS=$(date +%s); NONCE=$(openssl rand -hex 8)
BODY='{"player_id":"p123"}'
SIG=$(printf "POST\n/api/v1/sessions\n$TS\n$NONCE\n$(printf '%s' "$BODY" | openssl dgst -sha256 | cut -d' ' -f2)" \
  | openssl dgst -sha256 -hmac "$OPERATOR_SECRET" | cut -d' ' -f2)
curl -X POST https://api.ura-dhura.com/api/v1/sessions \
  -H "Content-Type: application/json" \
  -H "X-API-Key: $OPERATOR_KEY_ID" \
  -H "X-Timestamp: $TS" -H "X-Nonce: $NONCE" -H "X-Signature: $SIG" \
  -d "$BODY"

Response (data envelope omitted for brevity):

{
  "session_id": "dl-sess-…",
  "session_token": "gst_…",
  "table_id": "teen-patti-low",
  "launch_url": "https://api.ura-dhura.com/api/v1/provider/launch/gst_…",
  "websocket_url": "https://api.ura-dhura.com/ws/game",
  "expires_at_ms": 1767531600000
}
Field name. The per-player play URL is called launch_url in the response (there is no separate play_url field). Open it in a WebView or browser — it redirects to the game with the session attached.

Sample: Place Bet

curl -X POST \
  https://api.ura-dhura.com/api/v1/games/teen-patti-pro/rooms/default/bets \
  -H "Authorization: Bearer <session_id>" \
  -H "Idempotency-Key: <uuid>" \
  -H "Content-Type: application/json" \
  -d '{"position":"A","amount":100}'

position is the seat (A/B/C); amount must be one of the configured denominations (20 / 100 / 500 / 1000 by default). The room segment is informational — the room is resolved from the Bearer session, so a mismatched room cannot bet into another table. Reusing an Idempotency-Key with the same payload replays the original acceptance; reusing it with a different payload is rejected as DUPLICATE_REQUEST.

Event contract

Every event emitted on the socket carries an event_id (uuid4, unique per emit) and the round's state_version (an integer that increments on every round state change). An animation is idempotent if it is keyed on event_id: a redelivered event over a reconnecting socket then cannot replay the effect. seq remains for ordering but is not unique across a resubscribe replay, so it is not an idempotency key.

{
  "kind": "event",
  "data": {
    "seq": 7,
    "event_id": "3f2c9a1b6d4e4f8a9b0c1d2e3f4a5b6c",
    "state_version": 4,
    "kind": "bet.accepted",
    "serverTime": 1767528000000,
    "round_id": "teen-patti-low-r4",
    "player_id": "…",
    "position": "A",
    "amount": 100
  }
}

Round lifecycle, in the order the server emits it: ABOUT_TO_START → BETTING_OPEN → BETTING_CLOSED → RESULT_PROCESSING → RESULT → RESULT_DECLARED → SETTLED → CLOSED. SETTLED_PENDING and SETTLE_FAILED exist for the settlement-retry path and are not normal gameplay states.

ABOUT_TO_START lasts about a second after a round is dealt. The betting deadline does not start until the window opens, so it is presentation time, not lost betting time -- and no bet is accepted there. RESULT_DECLARED is the published outcome held about 2.2s while the reveal plays; money moves only at settlement.completed. A settled result is then held about 6s before the next round is dealt, so the outcome is actually watchable.

Hands. During betting each seat's hand arrives as one revealed card plus two backs, e.g. {"A": ["3S", "**", "**"]}. The other two turn face-up at result.declared and stay up through settlement. A client must draw exactly what the snapshot shows -- face-up art for a code, the back for "**" -- and never decide visibility itself.

Spectators. A session with no seat (mySeat empty, e.g. a full table) receives the same snapshots and the same events, but may not bet: chips and repeat are inert. Everything animates normally.

Animations

Every effect is driven by a server event. Nothing is triggered by a local timer, a guessed state, or an optimistic update — if the server has not accepted it, it is not animated. A rejected bet produces no flight, no stack change and no balance movement.

EventEffect
round.created / new round_idCards sweep back to the deck, then deal to A/B/C with a stagger along a bezier arc.
snapshot status: BETTING_OPENCountdown recomputed from betting_end_at every frame. The timer badge shows seconds while betting, 0 once closed, an ellipsis while the result computes, and a star once published — never a raw status enum.
bet.acceptedOne chip flies from the tray to the correct seat on a bezier arc, lands with a bounce, and the stack grows. Uses the chip art for that denomination — no gradient, no printed value. Keyed on event_id, so a redelivered event cannot fly a second chip.
betting.closedControls disable immediately, in-flight chips finish cleanly.
result.publishedCards turn face-up, winner chair rings gold, winner badge appears on the winning seat, payout floats up. The badge sits on the chair because there is no free 80px band on a 390x844 canvas — an earlier version covered all three betting panels.
settlement.completedBalance updates. Never before this event; the wallet is the only authority.

Result dwell. A settled round is held about 6 seconds before the next is dealt. Without it, close → publish → settle → next all ran inside one tick and a client never observed a result state at all: cards never turned over, the winner never lit up, and the table looked like it skipped from betting straight to the next round.

Reconnect and resume. On socket drop the client re-subscribes and reads state_version from the snapshot. Equal means nothing was missed and no animation replays; higher means only the transition is animated. The seat is re-bound through reconnect, and a snapshot refetch alone never re-triggers an effect.

Reduced motion. With prefers-reduced-motion: reduce every animation returns immediately: the deal, the chip flight, the flip, the winner glow and the timer pulse all short-circuit, and the table renders its settled state directly. Functional feedback is unaffected — only the movement is removed.

WebSocket Events

Connect to the websocket_url from the session response, then send {"action":"subscribe","session":"<session_id>"} (room is taken from the session, never from the client). Either side may send {"action":"ping"}; the server answers {"kind":"pong"}. Snapshots arrive as {"kind":"snapshot","data":{…}}; errors as {"kind":"error","data":{"code":…}}.

Naming. The wire protocol uses the dotted SRS §8 names below, not SCREAMING_CASE. Map them 1:1 when bridging to another convention. This table is generated from the server's own emit sites and its webhook allowlist -- there are 20 names, no more, and an unlisted kind never arrives.
Wire event (kind)Meaning
game.session.createdA session was minted.
player.joined / player.leftMembership changed. The engine keeps the seat by player identity, so a rejoin is a no-op for seating.
round.createdA new round object exists, in ABOUT_TO_START.
round.startedThe round's timer and seed are set. (No round.opened exists -- that name was wrong in this table and has been removed.)
betting.openedThe window is live; countdown runs to betting_end_at. Emitted when ABOUT_TO_START ends.
bet.acceptedA bet was accepted with bet_id, position and amount. This is what the chip-flight animation is keyed on.
bet.rejectedA bet was refused. synchronous rejections also arrive as error.
betting.closedBETTING_CLOSED -- no further bets accepted.
result.processingThe result is being evaluated server-side.
result.publishedThe outcome was calculated, with winners and full hands.
result.declaredRESULT_DECLARED -- the published outcome, now held while the reveal plays. Every remaining card is face-up from this event on.
settlement.startedSettlement began.
settlement.completedMoney moved: pot, rake and carry_out included, exactly once per bet_id. This is the only event that may move a balance.
settlement.pending / settlement.failedSettlement-retry path. pending is retryable; failed should alert. Neither is normal gameplay.
balance.updatedA balance changed; re-read the authoritative value from the wallet.
session.completedA session ended.
round.cancelledA round was cancelled.
errorFailure with data.code (e.g. UNAUTHENTICATED, BET_REJECTED).

There is no round.closed event and no round.updated event. Both names appeared in an earlier version of this table and neither is emitted: a round ends when its status reaches CLOSED, and state changes arrive as the specific events above. If your integration listens for either of those two names, nothing will ever arrive.

Integration (DearLive)

Step 1 — backend mints a session per player. Your server calls POST /api/v1/sessions with its HMAC credentials (sample above). Store the session_id; hand the launch_url to the client.

Step 2 — open the play URL in a WebView. Load the launch_url fullscreen. It 302-redirects to the game with the session attached — no cookies, no extra auth step, no HMAC secret on the device.

Step 3 — implement the 4 wallet callbacks described in docs/INTEGRATION.md (balance, debit, credit, refund/status) so the game server can settle against the DearLive wallet. Until then the game runs in its standalone mode; wallet-dependent calls return 503 WALLET_UNAVAILABLE / WALLET_NOT_CONFIGURED, never a fake balance.

One-line install

The installer asks for the operator key and HMAC secret your account manager gave you, writes a .env at mode 600, adds it to .gitignore, scaffolds the client for whichever stack it finds, and verifies the API answers. Read it before you pipe it anywhere — that is the point of it being a readable file.

curl -fsSL https://api.ura-dhura.com/install | bash

Run it inside your project directory. With no project present it writes the .env and stops rather than guessing where your code lives.

Flutter (BLoC)

Dependencies: dio: ^5.0.0, web_socket_channel: ^2.4.0.

The client never mints its own session. Your backend holds the HMAC secret and calls POST /api/v1/sessions; the app receives a launch token and opens the table with it. Putting the secret in the app would publish it to anyone who unzips the build.

// 1. Your backend mints, the app redeems.
final launchToken = await myBackend.mintSession(playerId: 'player_1');

// 2. Open the table. This 302-redirects into the client with the session on.
final tableUri = Uri.parse('$api/api/v1/provider/launch/$launchToken');
await WebViewController().loadRequest(tableUri);

// 3. Round state arrives over the socket. The server is authoritative: the
//    BLoC renders snapshots and events, and computes no outcome of its own.
final channel = WebSocketChannel.connect(wsUri);
channel.sink.add(jsonEncode({'action': 'subscribe', 'session': sessionToken}));
// BLoC: one event in, one immutable state out.
sealed class RoundEvent {}
class RoundSnapshot extends RoundEvent { final Map<String, dynamic> data; RoundSnapshot(this.data); }
class RoundUpdate   extends RoundEvent { final String kind; final Map<String, dynamic> data; RoundUpdate(this.kind, this.data); }
class RoundFailure  extends RoundEvent { final String code; RoundFailure(this.code); }

class RoundBloc extends Bloc<RoundEvent, RoundState> {
  RoundBloc(WebSocketChannel ch) : super(const RoundState.idle()) {
    on<RoundSnapshot>((e, emit) => emit(RoundState.ready(e.data)));
    on<RoundUpdate>((e, emit) => emit(
        e.kind == 'result.declared'
          ? RoundState.settled(e.data)      // reveal cards here
          : state.copyWith(lastEvent: e.kind)));
    on<RoundFailure>((e, emit) => emit(RoundState.failed(e.code)));
  }
}
Bet rejections are not round events. A refused bet comes back as {"kind":"error"}, not as an event in the stream. Handle it separately or a full table reads as a silent no-op.

NestJS wallet callbacks

The game server calls your service to move money, in four operations. Each one is retried until it gets a 2xx, so every handler must be idempotent: charge on the transaction id, not on arrival.

OperationYour side doesOn success return
balanceRead the player's available balance.the balance
debitTake the stake. Exactly once per transaction id.the new balance
creditPay a win. Exactly once per transaction id.the new balance
rollbackReverse a debit that never completed.the new balance

Verify before you trust. The provider signs the raw request bytes with HMAC-SHA256 over the timestamp and nonce. Compare in constant time, reject a timestamp outside your window, and remember the nonce — without those two checks a captured request replays.

import { Controller, Post, Headers, Req, Res,
         UnauthorizedException } from '@nestjs/common';
import { createHmac, timingSafeEqual } from 'crypto';

const TOLERANCE_MS = 5 * 60 * 1000;

function verify(raw: Buffer, h: Record<string, string>, secret: string) {
  const ts = h['x-timestamp'] ?? '', nonce = h['x-nonce'] ?? '',
        sig = h['x-signature'] ?? '';
  if (!ts || !nonce || !sig) return false;
  if (Math.abs(Date.now() - Number(ts)) > TOLERANCE_MS) return false;
  if (seenNonce(nonce)) return false;           // replay
  const expected = createHmac('sha256', secret)
    .update(Buffer.concat([Buffer.from(ts), Buffer.from(nonce), raw]))
    .digest('hex');
  const a = Buffer.from(expected, 'utf8'), b = Buffer.from(sig, 'utf8');
  return a.length === b.length && timingSafeEqual(a, b);
}

@Controller('teen-patti/wallet')
export class WalletController {
  @Post()
  async handle(@Req() req, @Headers() h, @Res() res) {
    const raw = req.rawBody ?? Buffer.from(JSON.stringify(req.body ?? {}));
    if (!verify(raw, h, process.env.OPERATOR_HMAC_SECRET!)) {
      throw new UnauthorizedException('bad signature');
    }
    // Dispatch on req.body.op, and key the ledger write on
    // req.body.transaction_id. A 5xx tells the server to retry; a 4xx tells
    // it the request is wrong and must not be.
    res.status(501).json({ error: 'wire this to your ledger' });
  }
}

MongoDB integration

There is no direct database access. The game server holds its own state and speaks REST and WebSocket only. Connect Postgres or Mongo to your side for your own reporting; do not point a second client at the game's store, and do not read settlement rows to decide a balance — ask the wallet callback, which is the authority.

If you keep your own copy of sessions, rounds or results, these are the constraints worth encoding as indexes rather than discovering in production:

// Unique keys are not optional: they are what makes a retry idempotent.
db.sessions.createIndex({ session_id: 1 }, { unique: true });
db.sessions.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 });  // TTL
db.rounds.createIndex({ room_id: 1, round_no: -1 }, { unique: true });
db.bets.createIndex({ bet_id: 1 }, { unique: true });
// Exactly-once payout. One settlement per bet, enforced by the database
// rather than by a check-then-insert in application code.
db.settlements.createIndex({ bet_id: 1 }, { unique: true });
The settlement index is the important one. A unique constraint on bet_id is what makes a duplicate credit impossible. Doing it in application code leaves a window between the read and the write, and the game server will find it.

Agora (video)

Agora is an independent layer. It carries voice or video for a table; it knows nothing about cards, rounds or balances, and the game server knows nothing about it. The two share a room identifier and nothing else.

// Independent of the game. The only shared value is a room name.
final agora = AgoraRtcEngine();
await agora.joinChannel(token: agoraToken, channel: roomId);

// The game client renders the table from its own WebSocket snapshot.
// A player joining or leaving Agora triggers nothing in the round state,
// and a round event must never be inferred from Agora's roster.

Keep the Agora token out of the game client and out of the launch URL: mint it in your backend, scoped to a channel and an expiry, and pass it to the app the same way you pass the launch token.

Next.js admin proxy

Proxy the admin API through your own origin so the operator key stays server-side. Replace X-Admin-Key; do not forward the caller's. Forwarding hands anyone who finds your route the ability to spend your operator's key.

// app/api/teen-patti/[...path]/route.ts
import { NextRequest, NextResponse } from 'next/server';

// An allowlist, not a pass-through. A proxy that forwards any path under
// /admin is a proxy for whatever else lives there.
const ALLOW = /^\/api\/v1\/admin\/(dashboard|packages|profit-risk|audit
  |players|games|rooms|sessions)/;

export async function proxy(req: NextRequest,
                            ctx: { params: Promise<{ path: string[] }> }) {
  const { path } = await ctx.params;
  const suffix = '/' + path.join('/');
  if (!ALLOW.test(suffix)) {
    return NextResponse.json({ error: 'not proxied' }, { status: 404 });
  }
  const upstream = await fetch(
    (process.env.GAME_API_URL ?? 'https://api.ura-dhura.com') + suffix,
    { method: req.method,
      headers: { 'X-Admin-Key': process.env.OPERATOR_API_KEY!,
                 'Content-Type': 'application/json' },
      body: ['GET','HEAD'].includes(req.method) ? undefined : await req.text(),
      cache: 'no-store' });
  return new NextResponse(upstream.body, { status: upstream.status,
    headers: { 'Content-Type':
      upstream.headers.get('content-type') ?? 'application/json' } });
}

Authorise the browser session in your own middleware before this route runs. The route above checks the path, not who is asking.

Error codes

Every response uses the same envelope, so an error always carries a code, never prose alone. Match on the code; the message is for humans and may change.

HTTPcodeMeansRetry?
401UNAUTHENTICATEDNo session, or it expired.No — mint a new one.
401INVALID_SESSION_TOKENLaunch token unknown or expired.No — mint a new one.
403FORBIDDENSigned, but not permitted.No.
403TBC_RULE_UNCONFIRMEDA real-money action was refused because a rule is still to-be-confirmed.No — confirm the rule.
404NOT_FOUNDUnknown room, round or route.No.
409BETTING_CLOSEDThe betting window for that round has closed.No — wait for the next round.
409DUPLICATE_REQUESTThat Idempotency-Key was already used.No — it already happened.
409STATE_CONFLICTThe room is in a state that forbids this (e.g. a seat is taken).No — re-read state.
422VALIDATION_ERRORBad field: not a chip, not a seat, over the limit.No — fix the request.
402INSUFFICIENT_BALANCENot enough funds for that stake.No.
429RATE_LIMITEDToo many mints. See limits.Yes, after the window.
503WALLET_UNAVAILABLEYour wallet service did not answer.Yes, with backoff.
503WALLET_NOT_CONFIGUREDNo wallet is wired up on this deployment.No — configure it.
500INTERNAL_ERRORServer fault. The detail is logged, not returned.Yes, with backoff.
Never retry a 4xx as-is. A VALIDATION_ERROR or BETTING_CLOSED retried unchanged fails identically. A 5xx or a 503 is the only case where the same request should be sent again — and then with the same Idempotency-Key, so a successful first attempt that lost its response is not charged twice.
